# Operator Web Control Surface

Beyond Discord mentions, the [[Architecture Overview|gateway]] exposes a second way to drive agent runs: an authenticated, browser-facing HTTP surface for human operators. An operator signs in with GitHub, launches a run against a bound repository, and watches its status and output stream back live. This page describes how that surface is structured and why its security posture is built the way it is.

The implementation lives under `packages/gateway/src/web/` (the HTTP server, routes, authentication, and SSE machinery) and `packages/gateway/src/operator-contract/` (the frozen data types the surface speaks). The decision to make the gateway the single authority for operator authentication — rather than maintaining a parallel system in the separate dashboard project — is recorded in `docs/decisions/2026-06-19-s2-operator-auth-authority.md`.

## Listener Topology

The operator server (`web/server.ts`) is a Hono application bound only to the gateway's internal network — never the public internet directly and never the sandbox network the workspace runs on. TLS is terminated upstream by an infrastructure reverse proxy at a configured public origin, so the listener itself receives plain HTTP from that proxy.

Because the server trusts a proxy in front of it, it validates the forwarded host and protocol headers against the expected public origin and rejects mismatches. This stops anything that can reach the listener from spoofing the operator origin. During graceful shutdown a drain gate refuses new requests with `503` before any request body is read, and unauthenticated routes carry small body-size limits and rate limiting keyed on the trust-aware resolved client address (the socket peer, unless that peer is a configured trusted proxy, in which case the address comes from walking its X-Forwarded-For chain to the first untrusted hop).

Routes fall into two classes, enforced by a registration seam (`web/operator-route.ts`):

- **Public** — the health check and the two GitHub OAuth endpoints (start and callback). Registered through dedicated public helpers so they are never wrapped by the privileged guard.
- **Privileged** — everything else: launch, run listing, run-stream, repo listing, the two approval endpoints, session info, CSRF token issuance, and logout. Registered through a helper that automatically wraps each handler in the browser guard (session + allowlist + CSRF/origin checks). A startup assertion fails fast if any `/operator/*` route was registered without going through these helpers, making "forgot to add the guard" unrepresentable.

### Dependency-gated registration

Beyond the public/privileged split, each route is mounted **only when every dependency it needs is present**. The app builder (`web/server.ts`) threads a bag of optional dependencies — the session store, the denylist cache, the binding lookups, the allowlist, the audit logger, the run index, the observation manager, the approval registry, and the launch admission gate — and registers a given route inside an `if` that requires all of its pieces. A repo-listing route, for instance, never mounts unless the session store, denylist cache, binding lister, allowlist, and audit logger are all wired. Partially-wired security dependencies (some browser-guard pieces present, others missing) are treated as a programming error and throw at startup rather than silently degrading.

This pattern trades a subtle risk: a missing dependency drops a route silently, and a dropped route looks like a 404 rather than an error. To close that gap, an offline route-registration smoke check (`web/operator-route-smoke.ts`) pins the complete expected inventory of operator routes and asserts the built app exposes exactly that set. If a dependency is accidentally removed from the wiring, the affected route vanishes from the app and the smoke check fails in CI — at image-build time, before the gateway ever serves traffic.

### The operator route set

The privileged surface currently exposes:

- `POST /operator/runs` — launch a run (see [Launching a Run](#launching-a-run)).
- `GET /operator/runs` — list runs across all bound, non-denylisted repositories.
- `POST /operator/runs/:runId/cancel` — request cancellation of an in-flight run (see [Cancelling a Run](#cancelling-a-run)).
- `GET /operator/runs/:runId/stream` — open the SSE observation stream for one run.
- `GET /operator/runs/:runId/approvals` — list the run's currently-open approval requests.
- `POST /operator/runs/:runId/approvals/:requestId/decision` — settle one approval request.
- `GET /operator/runs/:runId/questions` — list the run's currently-open agent-question requests.
- `POST /operator/runs/:runId/questions/:requestId/decision` — answer or skip one agent-question request. See [Answering Agent Questions](#answering-agent-questions).
- `GET /operator/repos` — list the bound, non-denylisted repositories the operator can launch against.
- `GET /operator/session` and `GET /operator/session/csrf` — current session info (with an optional coarse `push` health field — see [Push health](#push-health)) and a fresh CSRF token.
- `POST /operator/auth/logout` — end the session; the revoke is stored before the response (see [Sessions](#sessions-webauthsessionts)).

The unauthenticated set is just the health check and the two OAuth endpoints (`GET /operator/auth/github/start`, `GET /operator/auth/github/callback`).

## Authentication and Authorization

### GitHub OAuth (`web/auth/github.ts`)

Sign-in is a hand-rolled GitHub OAuth flow using PKCE and an anti-forgery `state` value. The start endpoint generates the PKCE verifier server-side (it is never written to a cookie or returned to the browser), stores the `state` server-side with a short TTL and an outstanding-attempt cap, and redirects to GitHub. The callback validates `state` as one-time, exchanges the code with the stored verifier, and reads the authenticated user's stable numeric GitHub ID and display login. The authorize request asks for the `read:user` scope, and the resulting token is used for that one `GET /user` call and then dropped: it is never stored, and the session store receives identity only. After the session is minted, the callback redirects to the validated `return_to` captured at start; when none was captured (for example, the start URL was opened directly) it redirects to a default landing path — the first entry of the return-path allowlist (`/operator` by default) — validated by the same same-origin allowlist check, so a misconfigured default can never become an open redirect.

The callback checks the operator allowlist before it creates anything, then creates the new session, then retires the session behind any stale cookie. A stale session of the same user is rotated, which writes the `rotated` status and fires no revoke hook. A stale session of a different user is revoked and fires the hook. If the store refuses the login (cap reached, a failed write, or a store that never loaded), or the stale session cannot be retired, the callback returns `503` with `Retry-After`, sets no cookie, and leaves any existing session valid.

Two properties matter throughout: the **numeric user ID is the authority** for every later authorization and audit decision, while the login is treated as mutable display metadata; and every authentication failure branch returns the same coarse response so the surface gives no oracle about why a request was rejected.

### Admission under capacity pressure

Unauthenticated request accounting uses a derived key from `web/ingress/resolve-client.ts`: IPv4 clients keep a /32 bucket, while native IPv6 clients share their /64 prefix's budget. Trust decisions and the OAuth callback binding still use the **exact canonical address**, so moving within a /64 does not bypass the address binding. Authenticated routes account by numeric operator ID. Health has an independent limiter, preventing routine probes from spending the sign-in budget.

The shared fixed-window limiter (`http/rate-limit.ts`) bounds its map to 10,000 keys by evicting the oldest window when a new key arrives at capacity. Hits do not promote a bucket; renewing an expired window moves it to the tail. This preserves admission for a new legitimate client instead of letting an address flood fill the map and deny everyone else. The tradeoff is explicit: an evicted active bucket loses its count, so the limiter is best-effort under cardinality pressure, not a hard adversarial quota.

The OAuth state store applies the same availability principle with a 1,000-entry bound. After stale-state reclamation, the per-accounting-key outstanding-attempt check, and start-request validation, a new state may evict the oldest remaining state. An evicted attempt's callback becomes an ordinary unknown-state rejection; it does not resurrect the state or trigger a retry bounce. This guarantees eligible starts can be admitted, not that every in-flight sign-in survives a flood. The PKCE verifier and exact-address binding remain attached to the newly minted state (`web/auth/github.ts`).

### Sessions (`web/auth/session.ts`)

A successful sign-in mints a server-side opaque session: a 256-bit random identifier in a `__Host-`-prefixed secure cookie with `Max-Age=604800`. The cookie carries only the identifier. The gateway holds the identity (numeric GitHub ID, login, issue time) and no credential of any kind.

**Lifetime.** A session lives 7 days from login. There is no idle timeout, and no request extends it. `GET /operator/session` reports that fixed expiry as `expiresAt`. A session survives a gateway restart. ASVS V7.1.1 asks for the session lifetime to be documented, with a justification for any deviation from NIST SP 800-63B re-authentication guidance. The justification for 7 days: one allowlisted operator, an installed app that is awkward to re-authenticate, a durable logout, a new identifier at every login, and a revoke-all control (see [Revoking every session](#revoking-every-session)).

**Persistence.** An in-memory map is authoritative for every request, so a request never touches the object store. Each session also has a record at `operator-web/sessions/{sha256(sessionId)}.json`, written with a conditional put before the session is accepted. The key is the hash of the identifier, so neither the key nor the record contains the identifier. The record holds the GitHub ID, login, issue time, a status (`active`, `revoked` or `rotated`), and an HMAC. The HMAC key is derived by HKDF from `GATEWAY_OPERATOR_CSRF_SECRET` with its own info label, and it covers the key hash and every field, so a record planted at a chosen key, or copied to another key, fails verification.

**Startup.** Before the operator server starts, the gateway runs a write/list/read/conditional-update/delete self-test on the session prefix, then loads every record. The load drops records that are expired, revoked, failing their HMAC, dated in the future, or belonging to a user no longer on the allowlist, and it durably revokes the non-allowlisted ones. Past the 10,000-session cap it keeps the newest and durably revokes the rest. A record whose read fails is retried once, and one that fails twice is counted and dropped without failing the load. A failed self-test, list or load never stops the gateway: the session store stays not ready, `create` refuses, login returns `503`, and no old session is accepted. Nothing retries; a restart does. The usual cause is a missing IAM grant (see the deploy runbook).

**Logout.** `POST /operator/auth/logout` writes the revoke first. A `200` means the revoke is stored; a `503` means it is not, and the session is still valid, so the operator retries. The in-memory revoke and the revoke hook run only after the write lands. The hook deactivates that operator's push subscriptions. A repeat logout succeeds without a second hook, and a rotation never fires it. A logout that arrives after a same-user re-login has rotated the session still persists `revoked` over the `rotated` record and fires the hook once; a rotation never overwrites a `revoked` record. A failed write emits `auth.revocation.persist_failed`. Revoked and rotated records carry a `revokedAt` time under the MAC. After a restart, the load replays the hook once per user who has a revoked record and no live restored session, which repairs a deactivation that failed earlier. The replay is fenced at the moment the load began: it leaves a subscription whose `updatedAt` is at or after that time, so a device the operator resubscribed after the restart is not switched off by a replay that finishes late. A revoked record stays replayable until `revokedAt` plus 7 days, even when the session's own 7 days have ended, so a restart within 7 days of the logout repairs it and a later one does not. If a revoked record cannot be read at a restart, that restart skips its replay, and a later restart within the window repairs it. Login validity is still judged on `issuedAt` alone. TTL expiry does not fire the hook.

**Retention.** An hourly timer scavenges expired and revoked sessions from the map and sweeps the object store. Each record is read and deleted as the sweep reaches it, with a conditional delete on the version it read, so a sweep cut off by its 30-second deadline keeps what it deleted. A sweep stopped by its 20,000-key limit does the same. Either way the next sweep resumes at the first key it had not reached and wraps round the listing, so retained records at the front cannot hide expired ones behind them. The sweep deletes a record at the later of `issuedAt` and `revokedAt` plus 7 days, and it deletes a malformed record at once, using a conditional delete on the version it read. A record that fails its HMAC is deleted only once its claimed `issuedAt` is more than 7 days old; a younger one is counted and kept, so a gateway started with the wrong secret, or a second writer with a different secret, cannot erase live sessions. A stored record is therefore kept until 7 days after login (7 days after the revoke for a revoked or rotated one) plus one sweep interval. Load and sweep clamp the effective revoke time to `issuedAt` plus 7 days, since a logout can only happen while the session is valid, so a wrong `revokedAt` (a forward clock step, for instance) cannot keep a record past `issuedAt` plus 14 days.

### Revoking every session

Rotate `GATEWAY_OPERATOR_CSRF_SECRET` and redeploy. Every stored record then fails its HMAC at the next load, and in-flight CSRF tokens fail with it. Use this for a stolen device or a suspected leak. The next sweep after each record's claimed 7 days deletes the stale records. Rotation does not deactivate push subscriptions, because records that fail their HMAC are never trusted and nothing is replayed for them. If push is enabled, sign in as the affected operator after the redeploy and sign out once: logout deactivates every push subscription tied to that operator's GitHub identity, including the one on the lost device, and the operator re-subscribes from the devices they keep. If signing in is not possible, delete that operator's records under `operator-push/subscriptions/by-endpoint/` (each names its operator ID).

### Allowlist and repository access (`web/auth/allowlist.ts`, `web/operator/route-helpers.ts`)

Authentication proves who an operator is; authorization decides what they may touch. A file-backed allowlist of stable numeric GitHub user IDs gates the surface, and it fails closed — a missing, unreadable, or malformed allowlist denies everyone. The browser guard checks it on every request, and the stream lease re-checks it on every tick.

Repository access is one predicate, `resolveRepoAccess`, used by every route that names a repository, for reads and writes alike: the repository must be bound **and** not denylisted. It reads the binding once on the server, then consults the denylist with the binding's deny keys. A malformed name is denied with no store call. A missing binding is denied. A store error is `unavailable`. Anything but allowed returns the same not-found response. No GitHub call is made, and the operator's GitHub rights are not consulted. A write route therefore does not track what the operator can do on GitHub: access follows the binding. The GitHub-side action on dispatch and launch runs as the Fro Bot GitHub App installation, not as the operator.

Because the binding is the grant, only the configured Discord binders can create one. `/add-project` refuses anyone not listed in `GATEWAY_BINDER_ALLOWLIST_FILE` (Discord user IDs, one per line), on top of the guild-level `ManageChannels` check. An empty list refuses everyone and logs a startup warning. The installation scope of the Fro Bot GitHub App bounds which repositories a binder can bind.

### CSRF and the browser guard (`web/auth/csrf.ts`)

The browser guard validates Fetch Metadata headers and an HMAC-signed CSRF token on mutating requests (`POST`/`PUT`/`PATCH`/`DELETE`); safe methods are exempt. Combined with the same-origin posture from the listener topology, this is what makes the privileged routes safe to expose to a browser. The token binds `sha256(sessionId)`, the operator ID and a 15-minute interval (with a 30-second grace window), and its payload carries the hash, never the session identifier. The guard reads the session map only; it never extends a session.

## Launching a Run

### Checkout preparation and recovery

Gateway runs prepare the persistent checkout before the `EXECUTING` transition, under the shared repository lock (`execute/run.ts`, `workspace-api/client.ts`). Preparation asks the workspace-agent to update first; only a `no-checkout` result leads to a fresh clone and another update. A ready result includes remote default-branch evidence and a starting checkout observation. The engine records this as checkout provenance on the run and adds a deterministic line to its human reply, rather than trusting model-generated claims about what commit it saw. An ineligible tree — dirty, detached, on another branch, diverged, or obstructed — ends the run before execution; an uncertain network or apply result is recorded as a failure, not silently treated as a clean checkout. See [[Architecture Overview]] for the workspace-side mutation boundary.

The gateway's Discord recovery command and its Recover button preview a preserve-and-replace operation before confirmation. The workspace-agent checks that the checkout still matches the preview fingerprint, moves the existing tree into a quarantine backup, and publishes a fresh default-branch checkout. Per-repository mutexes and persisted journals prevent another mutation from racing the operation or treating an interrupted update as a clean starting state (`apps/workspace-agent/src/recover.ts`, `apps/workspace-agent/src/update.ts`). If a subprocess cannot be confirmed stopped, the workspace holds that repository against further mutation until restart. The gateway's run lock and the workspace mutex protect different boundaries: gateway-run execution per repository and local checkout operations, respectively.

### Browser launch

`POST /operator/runs` (`web/operator/launch-route.ts`) is a fire-and-return endpoint: the operator submits a repository and a prompt, and the server responds `202` with a `runId` almost immediately, leaving the operator to observe progress over SSE. Before anything launches, the request passes an ordered gauntlet: the browser guard, an operator-keyed rate limit, session identity resolution, body validation, **server-owned binding resolution** (the client names a repo but the server resolves the actual binding — client-supplied paths or owners are ignored) followed by the denylist check, both inside the single repo-access predicate, and finally a per-operator idempotency guard.

The idempotency guard (`web/operator/idempotency.ts`) namespaces its key by the operator's numeric ID (`{githubUserId}:{clientKey}`), so one operator can never suppress another's launch. It uses a two-phase reserve-then-commit lifecycle: the key is reserved before `launchWork` is called and committed only on success, so a concurrent duplicate during the reservation window is recognized as in-flight rather than launching the work twice. On rejection the reservation is rolled back so no dead `runId` is echoed.

Admission itself goes through the gateway's single `launchWork` gate (see [[Execution Lifecycle]] for how that same admission path now records queued and failed runs).

## Dispatching a GitHub Action Run

Launching is not the only way to start work from the browser. `POST /operator/dispatch` (`web/operator/dispatch-route.ts`) triggers the Fro Bot **GitHub Action** in the target repository rather than a gateway-hosted run — the same capability the Discord `/dispatch` command exposes, projected onto the web surface.

The route deliberately owns nothing but the operator gate stack and the response projection; all GitHub authentication and workflow-dispatch behavior lives in the injected, transport-neutral `DispatchWorkflow` (`github/dispatch.ts`), which Discord and the web share unchanged. Its gate ordering mirrors the launch route — browser guard, operator-keyed rate limit (deliberately tighter here: three per minute, ten per hour), session identity resolution, body validation, the repo-access predicate (server-owned binding resolution, then the denylist), and finally a per-operator idempotency reservation so a retried POST dispatches once. Dispatch uses the same predicate as every read route, and the workflow dispatch itself runs as the Fro Bot GitHub App installation, not as the operator.

The response shape is the notable design decision. Dispatch has many ways to not-happen that are not server errors — the GitHub App is not installed, it lacks the Actions permission, it is missing other permissions, the repository or workflow cannot be found, the task text is invalid, or GitHub rejects the dispatch. All nine `DispatchOutcome` variants are returned as `200 {outcome}` rather than mapped onto HTTP status codes, so a browser client branches on one discriminated union instead of guessing intent from a status. Several of those variants carry an installation URL to make the failure actionable.

The audit boundary is drawn tightly around that: an audit event records the outcome discriminant, the repository key, and an optional run ID — never the task text and never the install URL — and no audit event fires at all on a repo-level denial, whether the repository is unbound or denylisted, so the audit log itself cannot become a repository-existence oracle. Correlation identifiers are minted per request and are never the session ID.

## Listing Runs

`GET /operator/runs` (`web/operator/runs-route.ts`) answers "which runs may I see right now?" without the operator first having to know a `runId`. It enumerates bindings, drops denylisted repositories, deduplicates the rest by `owner/repo` so a repository bound to several channels is listed once, caps the count before any run-state read, and projects each surviving run through the `RunSummary` shape (`operator-contract/run-summary.ts`). The listing is bounded — it returns at most a fixed number of summaries — and each summary carries only the run id, the `owner/repo` from the binding (never the internal entity reference), a status, and timestamps. The status uses the stream's vocabulary: a `running` run with a pending approval lists as `waiting_for_approval`, and one with only a pending question lists as `waiting_for_question`. The route reads the same request registries and applies the same overlay rules as the stream (see [The Operator Contract](#the-operator-contract)), so queued and terminal runs keep their lifecycle status. Like the other dependency-gated routes, it mounts only when both the approval and question registries are wired. Runs whose stored entity reference disagrees with the binding (a sign of storage corruption or a repository rename) are dropped rather than rendered, so a stale record can never surface another repository's work.

The run index this route reads from is server-owned; the operator never supplies a run-to-repository mapping. See [[Session Persistence]] for how the index scans recent run records by recency from the object store.

## Approving Tool Use

Web-launched runs are no longer approval-free. When OpenCode hits a permission gate mid-run — a shell command, an out-of-tree file write — the same approval registry that backs Discord buttons (`registry.handleDecision` as the single settlement authority) also drives the web surface.

The web approval transport (`web/operator/web-approval.ts`) follows a **register-before-fan-out** discipline: it registers the pending request in the shared registry first, attaches the settle/clear callback, and only then fans an SSE frame out to any watching browsers. If the fan-out throws, the error is logged and swallowed — the registry entry already exists and its deadline still settles fail-closed, so a dropped frame degrades the UI without weakening the gate.

Operators observe and settle approvals two ways. The SSE stream carries **approval frames** (described below), and `GET /operator/runs/:runId/approvals` (`web/operator/pending-approvals-route.ts`) is a reconciliation fallback: a browser that reconnects after a dropped stream can re-fetch the currently-open requests instead of waiting for a replay. Listing approvals and settling one, via `POST /operator/runs/:runId/approvals/:requestId/decision` (`web/operator/decision-route.ts`), use the same repo-access predicate. The decision route resolves the run to its repository through the server-owned run index, re-runs that predicate, and hands a transport-bound operator identity to `registry.handleDecision`, which records the `once` / `always` / `reject` outcome as the authoritative settlement.

## Answering Agent Questions

When an agent calls OpenCode's `question` tool, the run blocks until the request is answered, skipped, or expires. A question from the root session or an adopted background child reaches operators; one from a session the run does not own is ignored. Questions are a second family of the same request gate that backs tool approvals (see [[Architecture Overview]]), so each request settles exactly once across web answers, Discord answers, skips, the deadline, cancellation, and OpenCode's own echo.

The web question transport (`web/operator/web-question.ts`) follows the same **register-before-fan-out** discipline as approvals: the run's question coordinator registers the request first, and the transport then emits the SSE open frame and attaches the settle callback. A throwing observer is logged by request id and swallowed; the registry entry and its deadline are already in place.

**Routes.** `GET /operator/runs/:runId/questions` (`web/operator/pending-questions-route.ts`) is the reconciliation read: it is rate limited per operator, and returns at most 50 bounded request records. It finds questions by the asking run's id, so a Discord-launched run's questions are listed the same as a web-launched run's. `POST /operator/runs/:runId/questions/:requestId/decision` (`web/operator/question-decision-route.ts`) uses the same repo-access predicate. A web operator whose binding check passes can answer any run's question, including one a Discord run asked; a Discord user, by contrast, can settle only a question from their own thread. The body is checked against a 64 KiB limit before anything else. The route resolves the run to its repository through the server-owned run index, applies the repo-access predicate, and builds the operator actor server-side from the session. Every denial in the session, run lookup, and repo-access steps returns the same no-oracle not-found response.

**Request body.** `{decision: 'skip'}` skips the request. `{decision: 'answer', answers}` answers it with one entry per question, in order: `{options?: number[], text?: string}`. Options are zero-based indices into that question's `options`, not labels. The labels an operator sees are length-bounded and control-stripped and can differ from the raw labels the agent sent, so the gateway maps each index back to the raw label before replying. `text` is a free-text answer, accepted only when the question's `custom` flag is true, and capped at 4,000 characters. The response is `200 {state}` with `claimed`, `already_claimed` (another submission for this request is still in flight, including a second answer; the request reopens if that reply fails), `already_settled`, or `failed_to_settle`, or `400 {error: 'bad request', reason, questionIndex}` for a refused answer (the standard operator error envelope, with the refusal detail alongside; `questionIndex` is null when the problem concerns the whole request); a refused answer leaves the request pending. A request settles as a whole, so one decision carries answers for every question in it.

**Skip, deadline, and cancel.** Skip replies to the agent with an empty answer per question. The agent sees the question as unanswered and continues. An expired deadline does the same, and a question asked when the run has too little time left for a deadline is skipped immediately. Rejecting a question ends the agent's turn upstream, so the gateway rejects only when a run is cancelled or torn down, or when a `question.asked` payload is malformed.

**Untrusted text.** Every question header, text, option label and description, and every answer is untrusted plain text. The gateway carries these strings verbatim apart from length bounding and control-character stripping, never pre-renders them as HTML or Markdown, and never logs them or puts them in audit events or push payloads. Clients must display them as inert text.

**Discord.** For a Discord-launched run, the same request also appears in the run's thread. A single-question request that fits Discord's component limits renders natively with buttons or a select, Skip, and a text-answer modal when a custom answer is allowed. Any other shape posts a short notice saying a question is waiting and can be answered on this operator surface, and carries no question text. The request stays answerable here either way, and a Discord delivery failure never settles it.

## Cancelling a Run

An operator can stop a run that is still in flight. `POST /operator/runs/:runId/cancel` (`web/operator/cancel-route.ts`) applies the same repo-access predicate as the other routes. The route resolves the run to its repository through the server-owned run index, re-runs the predicate, and (deliberately) applies the operator-keyed rate limit only _after_ it so a denied caller never consumes budget.

Under the hood, cancellation rides an in-memory abort registry (`execute/abort-registry.ts`). When a run reaches the `EXECUTING` phase, the engine registers a per-run `AbortController` in the registry and composes the run's effective signal as `AbortSignal.any([timeoutSignal, cancelSignal])`; the controller is always removed in the outer `finally` regardless of how the run settles. Registration happens only after the `EXECUTING` transition commits — the earlier window is guarded instead by the run-state conditional-write rendezvous. A cancel request simply fires the registered controller.

Two design choices keep cancellation correct under races. First, classification is a **registry probe**, never composite abort-reason inspection: `AbortSignal.any` propagates whichever child fired first, so reading the reason would be racy, and the registry's own controller state is treated as ground truth (`execute/cancel.ts`). Second, a cancelled run settles as `CANCELLED` rather than `FAILED` — it flushes partial output, notifies the SSE observer, and suppresses the user-facing failure reply. The cancel path stops the heartbeat _first_ because its returned etags are the only fresh conditional-write handles; using a stale etag on the subsequent transition would `412` silently and TTL-orphan the coordination lock rather than fail loudly. When an operator cancel wins an adoption race, the losing run re-reads run-state, sees a `CANCELLED` phase, and exits cleanly instead of logging a misleading error. The `CANCELLED` phase is one of three [[Execution Lifecycle|terminal phases]] the coordination layer now names explicitly through a shared `TerminalPhase` type.

## Observing a Run

`GET /operator/runs/:runId/stream` (`web/sse/run-stream-route.ts`) opens a Server-Sent Events stream. The route resolves the run to its repository through a server-owned run index (never a client-supplied mapping), re-runs the repo-access predicate, and acquires a per-operator stream-slot lease (a small cap on concurrent streams per operator). Every failure on the authorization path returns the identical generic not-found shape; exhausting the stream-slot cap returns an honest `429`. There is deliberately no distinguishable "authorized but not streaming" response, because that would leak whether a run exists.

Once open, the stream emits a closed set of frame types: a **status** frame carrying the operator-safe run projection, **output** frames (incremental deltas plus a final terminal frame that supersedes them), **approval** frames for the tool-approval flow, **question** frames for agent questions, periodic **heartbeat** comments to keep proxies from closing the connection, and a **reset** frame with a typed reason on terminal status, shutdown, or overflow. A continuous authorization lease re-verifies the session, the allowlist, and repo access (binding and denylist) on an interval; if any check fails the stream closes gracefully. A logout, a rotation or a revoke removes the session from the map, so the next lease tick closes that operator's streams.

An approval frame comes in two shapes (`operator-contract/approval-frame.ts`): an **open** frame carries the request id, the permission kind, and — when relevant — a length-bounded, control-character-stripped command or filepath, so the browser can render the prompt; a **settle** frame carries only the request id, telling the browser to dismiss a prompt that has been answered (by this operator, another operator, or the registry deadline). Unlike output deltas, approval frames are never coalesced — they are rare and must arrive intact.

A question frame (`operator-contract/question-frame.ts`) has the same two shapes. An **open** frame carries the request id, the run id, and for each question its header, text, options (label and description), and the normalized booleans `multiple` and `custom` (`custom` is true unless the agent explicitly disabled it). Every string is length-bounded and control-character-stripped, and none is rendered. A **settle** frame carries only the request id, run id, and `settled: true`, and tells the browser to dismiss the prompt whether it was answered, skipped, expired, or torn down. Question frames are never coalesced, and the manager enqueues a request's settle frame before the run's terminal status. Unlike approval frames, open question frames are replayed: a subscriber that connects while a question is pending receives the open frame, and a settled question never reappears. The replay set is bounded to 8 open requests per run, oldest evicted first, and is cleared when the run reaches a terminal status. `GET /operator/runs/:runId/questions` is the fallback when a replay is not enough.

Fan-out is handled by an in-memory observation manager (`web/sse/manager.ts`). The run engine calls into the manager on every state transition; the manager projects the run state through the redaction bridge, caches the latest status, and enqueues frames per subscriber without ever awaiting a write — a slow consumer is dropped locally once its queue exceeds a byte cap, and cannot stall publishing for anyone else. A bounded terminal-replay cache lets a late subscriber connecting shortly after completion still receive the final output and status before the stream closes. Once that cache no longer holds the run (TTL, caps, or a gateway restart), the run-stream route resolves the subscriber from the persisted run state instead: a terminal run gets its terminal status frame and the stream closes. Only the status is recoverable that way — persisted state carries no output text, so no final output frame is sent and clients must drive completion off the terminal status frame. The manager also re-derives each live run's waiting status from the request registries whenever a question or approval opens and whenever one is removed, so the live status and the reconnect replay change at that moment and not on the next lifecycle event. A settled request is removed only after its settle frame is enqueued, so the status still reads waiting right after that frame and returns to the lifecycle status once the last pending request for the run's scope is gone. A terminal run never flips back to waiting. The manager is observer-only: it can read and project run state but has no API to transition runs or touch coordination locks.

## The Operator Contract

The types crossing this boundary are defined once, in `packages/gateway/src/operator-contract/`, and treated as a frozen surface. The contract version (`version.ts`, currently `1.11.0`) is pinned at build time and never negotiated over the wire — clients cannot ask for an older shape. The version follows a deliberate increment policy: a major bump for any breaking change (a removed, renamed, or narrowed field), a minor bump for additive changes (a new optional field or a new type such as the `RunSummary`, approval-frame, and question-frame shapes), and a patch bump for documentation only. The version is also emitted (emit-only, never read from the wire) on the public health-check body, so operators can probe the deployed contract version without authenticating; note that adding that health field was treated as non-structural and did _not_ itself bump the contract version, because the dashboard enforces a fail-closed drift gate on the SSE ready-frame version. Contract 1.11.0 adds `waiting_for_approval` and `waiting_for_question` to the `RunSummary` status and gives question push notifications a run deep link; the dashboard's version pin must move with it. Contract 1.10.0 exports the closed set of push notification trigger kinds (`OPERATOR_PUSH_TRIGGER_KINDS` and `OperatorPushTriggerKind` in `operator-contract/responses.ts`); the dashboard's version pin must move with it. Contract 1.9.0 adds the question frame, the pending-question and answer/skip request types, and the `waiting_for_question` run status (`operator-contract/question-frame.ts`, `run-status.ts`); the dashboard's version pin must move with it. Contract 1.8.0 additionally carries validated checkout provenance for executing runs and a separate, bounded preparation reason for runs refused or failed before execution (`operator-contract/provenance.ts`); absent or malformed stored records never turn into a claim of freshness. Two normative obligations are encoded directly in the contract (`redaction.ts`):

- **Redaction obligation** — denylisted repositories must be excluded _before_ any per-repo query, not filtered at render time. Deny-key matching tolerates GitHub node-ID format skew by deriving the numeric database ID, and an entry with no usable deny key (or an unreadable denylist) must deny rather than leak. Redaction composes with repository access: the binding proves the repo is bound, redaction proves the repo _is not hidden by policy_, and both must pass.
- **Authorization obligation** — operator identity is always constructed server-side from the authenticated session and is never deserialized from a request payload, and approval/launch decisions must carry a transport-bound identity rather than a free-form caller string. Access to a repository follows its binding, not the operator's GitHub rights.

The projection helper (`sse/projection.ts`) enforces redaction structurally: it takes a denylist predicate as a required argument and returns nothing for a denied repository, so the operator-facing `OperatorRunStatus` (`run-status.ts`) exposes only safe fields (entity reference, surface, phase, status, timestamps, staleness) and never the internal coordination fields like holder or thread IDs. The phase-to-status mapping is part of the pure projection; the richer "blocked", "waiting for approval", and "waiting for question" states an operator sees are overlays derived from queue, approval-registry, and question-registry state rather than fields the projection itself produces. The same synchronous overlay serves the SSE status and the run list. Both waiting overlays apply only while the run is `running`, so queued and terminal runs keep their lifecycle status; when an approval and a question are pending together the status is `waiting_for_approval`, and it becomes `waiting_for_question` once the approvals settle. The overlay scope is the thread for a Discord run and the run for a web run.

The run-listing surface uses the `RunSummary` shape (`run-summary.ts`), which carries the `owner/repo` resolved from the binding rather than the internal entity reference, and the same status vocabulary as the stream, waiting overlays included. Both projections are pure and total: each returns nothing — rather than a partially-redacted record — whenever a repository is denylisted or a run's stored identity contradicts its binding, so callers skip the null and never render leaked or inconsistent data.

When a run fails, both projections may carry a `failureKind` — a coarse, sanitized reason drawn from a small closed vocabulary (`OperatorFailureKind` in `run-status.ts`): the two timeout variants (`inactivity-timeout`, `max-duration-timeout`), `stream-ended`, `workspace-unreachable`, `session-error`, `checkout-substituted`, `workspace-unavailable`, and an `unknown` fallback. The last two distinguish an untrustworthy checkout from unavailable workspace control; neither is falsely described as an ordinary transient OpenCode failure. The mapping from the engine's richer internal error kinds is an explicit allowlist, so any unrecognized or unmapped internal kind collapses to `unknown` rather than leaking implementation detail. A pre-acknowledgement startup failure surfaces as `workspace-unreachable`. The kind is persisted on the `FAILED` run-state transition and projected onto the operator surface, giving operators a stable, non-sensitive signal about _why_ a run ended without exposing stack traces or internal vocabulary.

The engine's newer `drain-timeout` kind — a run whose deadline expired while it was still waiting for background subagent work to settle — is mapped onto the existing `max-duration-timeout` rather than given a vocabulary entry of its own. That is a judgment about what the operator surface is for: a run's deadline covers execution and drain together, so from an operator's point of view it is the same wall-clock story, and the distinction only matters to someone reading the engine's logs. The internal-to-operator mapping table is exhaustiveness-checked against the internal kind union, so a future kind added without a mapping decision fails the type check rather than silently collapsing to `unknown`.

### Quarantined runs

A gateway run that fails while it may still own live background work is held rather than released. Instead of stopping its heartbeat and handing the channel's concurrency slot to the next queued run, it transitions to `FAILED` with a quarantine flag recorded on its run details, and a bounded hold window elapses before the heartbeat stops and the slot is freed. The lock is deliberately _not_ released on that path — lock takeover and force-release both require an expired lease plus a clear workspace status check, which is precisely why the hold has to be bounded rather than indefinite. Operators see an ordinary failed run; what they will notice is that the channel does not immediately accept the next run. Run details also carry the run's persisted ownership claim (its root session and not-yet-settled child sessions), which the gateway keeps as a diagnostic; on restart it checks the workspace status before terminalizing a stale run and never deletes locks. See [[Background Subagents and Ownership]].

## Audit

Security-critical events on this surface — sign-ins, allowlist decisions, launches, session revocation and restore, and stream lifecycle — flow through a typed audit seam (`web/audit.ts`) that records the numeric GitHub user ID and other safe fields while excluding tokens, prompts, and internal identifiers. Tool-approval and agent-question decisions are audited as `approval.decision` / `approval.rejected` and `question.decision` / `question.rejected`: a `question.decision` records the operator's numeric ID, the run and request ids, and an `answered` or `skipped` outcome, and a `question.rejected` records the same ids with a reason code (`already_claimed`, `not_found`, `invalid`, or `reply_failed`). Neither carries question or answer text. Session persistence adds two events: `auth.revocation.persist_failed` (a revoke that could not be written; the retry count and a coarse error class) and `auth.session.restore` (the startup restore, with its outcome, the failing phase when it failed, and counts of loaded, expired, revoked, not-allowlisted, unsigned, future-dated, over-cap and unreadable records). Neither carries a session identifier, hash, login or token. Repo-level denials (unbound or denylisted) emit no audit event at all. The push subscription lifecycle (subscribe, unsubscribe, deactivation, dispatch, and startup disablement — see [Operator Push Notifications](#operator-push-notifications) below) is folded into the same seam, holding to the same rule: only operator identity, coarse enums, and counts, never endpoints or key material.

## Operator Push Notifications

Alongside the SSE stream, operators can opt into browser push notifications for three events: a run entering `waiting for approval`, a run asking an agent question, and a run failing. Push is **opt-in and disabled by default** — a deployment must both provision VAPID key material and start the object-store CAS self-test successfully before the surface is registered at all (`program.ts`; see the [privacy and retention policy](../privacy/operator-push-retention.md) for what is stored and how it is deleted).

The surface exposes four authenticated operator routes (`web/operator-push/`):

- `GET /operator/push/vapid-key` — the current VAPID public key and key version, used by the browser to create a `PushSubscription`.
- `POST /operator/push/subscriptions` — register (or refresh) a subscription for the authenticated operator.
- `POST /operator/push/subscriptions/unsubscribe` — remove a subscription.
- `GET /operator/push/subscriptions` — list the operator's own subscription metadata (never the endpoint or keys — see `toSubscriptionMetadata` in `subscription-store.ts`).

**Broadcast model.** The operator dashboard is a shared surface, not a per-operator one — approvals are run-scoped, not operator-scoped, and there is no dashboard-operator identity available at the run-failed or approval-pending seams. Every opted-in operator with an active subscription is nudged, regardless of who launched the run. The notification payload is fixed and repo-neutral ("something needs attention, open the dashboard" plus an allowlisted failure label) so a broadcast never leaks run, repo, or prompt content — Discord and the SSE stream remain the authoritative, detailed channels; push is a fail-soft nudge on top.

**Question notification.** The `question` trigger sends fixed copy only: the title and body are the keys `operator.question_pending.title` and `operator.question_pending.body`, with `data: {type: 'question', runId, route: '/operator#<runId>'}`. The route deep-links the dashboard to the asking run. When the run id does not match `^[\w-]{1,128}$`, the payload omits `runId` and the route falls back to `/`. The builder takes only the run id, so question text, options, repo, and prompt cannot reach the payload. Approval and run-failed notifications keep `route: '/'`. It is sent for any run, Discord-launched or web-launched, once the question is registered.

**Dispatch and deduplication.** Only three lifecycle events fan out a push: a run entering the approval-pending state, a run registering an agent question, and a run reaching the `FAILED` phase. Neither successful completion nor an operator logout sends a notification (logout instead _deactivates_ that operator's subscriptions). The dispatcher (`web/operator-push/dispatcher.ts`) coalesces bursts through a bounded in-memory dedupe cache (`dedupe-cache.ts`, default five-minute window keyed by the run/approval id and event kind; one question nudge per run covers every question the run asks within the window), so a flurry of retries on one run does not spam every browser. Each broadcast records a single coarse `push.dispatch` audit entry carrying only delivered/dead/failed counts. When the push relay reports an endpoint is gone (HTTP 410/404), the dispatcher deactivates that subscription in place rather than retrying it.

**SSRF defense in depth.** Because a subscription endpoint is an attacker-influenceable URL that the gateway later makes an outbound request to, the surface guards it twice. A _parse-time_ check (`validate-endpoint.ts`, sharing IP classification with `ip-classification.ts`) rejects the endpoint as written at subscribe time — non-HTTPS schemes, loopback and private/link-local literals, and bare dotless hostnames are refused before a record is ever stored. A second _connect-time_ guard in the sender (`push-sender.ts`) closes the DNS-rebinding gap: it resolves the endpoint host itself, classifies every candidate address, and refuses to open the socket if any resolves into an internal range — so a hostname that passed validation but now points at a private IP still cannot reach the internal network. Endpoint URLs and key material are never logged; only coarse rejection-reason enums surface.

### Push health

Push is wired only after the startup CAS self-test passes, so a failure at or after boot would otherwise be invisible: the public health route cannot tell. The authenticated `GET /operator/session` response therefore carries an optional `push: {status}` field, where `status` is `ready`, `degraded`, or `unknown`. The field is **omitted entirely when push is not configured**, so those responses are unchanged, and `disabled` never appears on the wire. When the startup self-test fails, the push routes are not mounted, but the session route is, and it reports `degraded`. The public `GET /operator/health` is unchanged (`{ok, contractVersion}`), as are the ingress pipeline, rate-limit accounting keys, and the route inventory. The field is an additive, optional member of the operator contract (`OperatorSessionInfo.push`); a consumer whose parser sees a malformed value drops it and still accepts the session.

**Semantics.** The status is derived from a passive, in-memory tracker (`web/operator-push/push-health.ts`) that is created before the startup gate, seeded with the self-test result (its ticket is taken before the self-test, so the self-test's own later observations, such as a denied cleanup delete, supersede the seed), and updated only from calls that already happen. There is no polling, no persisted history, and no I/O when the status is read.

- `ready` means the subsystem was **observed ready** recently. It is **not a guarantee of delivery**: a relay "accepted" is not proof that a browser received the notification.
- `degraded` means the startup self-test failed or threw (held until restart), or the latest fresh observation of the store backend or of relay delivery failed.
- `unknown` means nothing fresh confirms readiness: every observation is older than one hour, or a failure aged out with no newer observation of that component. Stale never means "still healthy". (Before the startup self-test resolves the operator server is not yet serving, so `unknown` is not reported during startup.)

**Where observations come from.** Store backend health is observed at the object-store adapter the subscription store is built over (`web/operator-push/push-health-adapter.ts`, wired in `program.ts`), not at the store methods. `getObject` and `list` record a read; `conditionalPut` and `conditionalDelete` record a write. A call that completed — it succeeded, or the backend answered about the key — is `ok`: `NoSuchKey`/`NotFound`, `PreconditionFailed` (412) and `ConditionalRequestConflict` (409) by structured code, or a 404/412/409 status when there is no code. The code wins over the status, so a 404 `NoSuchBucket` is `failed`, as is any other error or a throw. A single CAS conflict is therefore not a fault, but when the store's own CAS retry loop exhausts (or a privacy delete loses its physical-delete race) the store reports a write failure, ordered by when that record finished (sweeps report once, after the loop), so a late report cannot supersede a newer successful write. A `markDead` cleanup that throws after a 410 is a backend failure only and never a relay failure. Because the store's results are otherwise not observed, an ownership denial, and a no-op success such as a logout that writes nothing, record nothing; a read inside a write method is a read; and a failed dead-subscription cleanup (`markDead`) is a write failure. Relay delivery is recorded once per broadcast by the dispatcher: any relay failure degrades, and a broadcast with at least one accepted send and no failures can clear it. Broadcasts that send nothing — no subscriptions, deduped, dead-only, or every record skipped as stale-key — record nothing.

Reads, writes, and relay are separate components. Each keeps the observation from the call that **started** latest, so an older call finishing late cannot overwrite a newer result, and a successful read cannot clear a failed write or a relay failure. There is no sticky "ever failed" flag: a later successful observation of the same component clears its failure. Staleness is measured on a monotonic clock, and an observation with a negative age is not fresh.

**Exposure.** Only the coarse status leaves the process, and only to an authenticated, allowlisted operator: no counts (not even zero or nonzero), timestamps, endpoints, hashes, ids, trigger kinds, error text, or VAPID material.

### VAPID key rotation and leak response

The VAPID private key is server-only, per-environment configuration — never logged, serialized, or returned by any route. Rotation supports a current key plus an optional previous key during a rollout window: each subscription record stores the key version it was created or refreshed under, and the dispatcher's trigger policy still delivers to previous-key records for the duration of the window (`web/operator-push/trigger-policy.ts`). Once the window closes, previous-key subscribers stop being notified until they re-subscribe under the new public key (their next browser-side subscribe call picks up the current key automatically).

If the private key leaks, the response is: provision a fresh VAPID keypair, roll the current key into the previous-key slot for a bounded rollout window, then retire the old key entirely once the window ends. There is no way to invalidate an individual leaked key server-side beyond this rotation — the protection comes from bounding how long the compromised key remains honored, not from revoking specific subscriptions.

## Implementation Reference

Symbol-level reference for mechanisms that [ARCHITECTURE.md](../../ARCHITECTURE.md) summarizes under Cross-Cutting Concerns.

### Approval Denial on Undeliverable Discord Notification

`createDiscordApprovalOnPending` (`packages/gateway/src/approvals/discord-transport.ts`) posts a tool-approval embed with Approve/Deny buttons and waits for a human. If the bound thread was deleted, that post fails, nobody can answer it, and the run would otherwise wait out its full budget for a decision that can never arrive. `handleUndeliverable` reclassifies a TERMINAL Discord failure — `UnknownChannel` or `MissingAccess`, matched on `DiscordAPIError.code` (a stable numeric code), never on `error.message`, so a wording change upstream cannot silently reclassify a rate limit or a 5xx as fatal — into an immediate server-side denial via `approvalRegistry.applySettlement({decision: 'reject', reason: 'disposed'})`, rather than leaving the entry `open` for a POST that can never succeed. Retryable failures (rate limits, 5xx, network errors) are left alone; the entry stays open via `markMessagePostFailed` so a later settlement can still deliver once the transient condition clears. The denial is deliberately visible, not silent: it logs at `error` with the Discord code, and posts a best-effort thread note worded distinctly from a human "Deny" click or a deadline timeout — because this mechanism turns Discord notification availability into a denial control, and an operator diagnosing a run must be able to tell a delivery failure from a person saying no.

### Agent Questions (Gateway)

When an agent calls OpenCode's `question` tool, OpenCode emits `question.asked` and blocks the tool call until the request is replied to or rejected. The gateway treats the request as a second family of human wait, next to tool approvals. A `question.asked` from the root session or an adopted background child reaches operators; one from a session the run does not own is ignored.

**One gate, two families.** `createRequestGate` (`approvals/request-gate.ts`) owns what must be identical for approvals and questions: the entry map, the `open → claimed → confirmed` state machine with a single-winner claim, the scope check, the registry-owned deadline timer and its claimed-vs-deadline handshake, authoritative echo settlement, run teardown, and exactly one terminal notification per request. `registry.ts` (approvals) and `question-registry.ts` (questions) each supply their own decision vocabulary and per-entry behavior on top. Nothing settles a request except through the gate. OpenCode's `question.replied` / `question.rejected` echo is authoritative; an echo for an entry nobody on the gateway claimed still settles it.

**Skip is an empty reply; reject is for teardown.** A skip, and a deadline expiry, reply to OpenCode with an empty answer for every question. Upstream turns that into an "Unanswered" tool result and the agent continues. Rejecting would raise `Question.RejectedError`, which `processor.ts` treats as a blocked turn that ends the agent's turn. Reject is therefore used only on cancel and run teardown, where ending the turn is the intent. A malformed `question.asked` whose request id is readable is rejected immediately (`QuestionCoordinator.onMalformed`), so the agent does not block until the inactivity timeout; an unreadable one is only logged. An ask over the count caps (`MAX_QUESTIONS_PER_REQUEST` = 8 questions, `MAX_OPTIONS_PER_QUESTION` = 64 options per question; upstream sets none) takes the same path with reason `oversize`: it is rejected, never stored, and never reaches SSE, push, or Discord. The registry refuses an oversize registration too, as a second line.

**Mandatory deadline.** A question registers with a positive deadline or not at all. The coordinator derives it at ask time from the budget the run has left (`computeApprovalDeadlineMs`: at least 60 s, at most half the remaining budget, 30 s clear of the hard abort, capped at 13 minutes). When the run has 90 s or less left, the question is skipped immediately with an empty reply rather than registered, because an entry with no deadline would block the agent until the hard abort. The deadline is a skip, so an unanswered question never fails the run.

**Human-wait gauge and drain.** `run-core.ts` keeps a gauge of request ids a human still has to settle, approvals and questions alike. The inactivity watchdog is paused while the gauge is non-empty and re-armed with a fresh window only when the last id is released. The guard lives in the one re-arm path (`resetInactivity`), so activity (text deltas, tool completions, an owned child, a parallel tool) never re-arms the watchdog while any wait is held or while the run drains; only releasing the last wait outside drain does. Release comes from OpenCode's echo and from the gate's per-request terminal notification (`requestGate.onTerminal`), which also fires for settlements that produce no echo: deadline skip, failed reply, teardown. Both directions are idempotent by request id, and a skipped-without-registering question releases its own wait. The gauge never influences drain: human waits are independent of completion, which requires ledger settlement, each child's notice or cancel evidence, and root freshness (see the drain-completion gate in [[Background Subagents and Ownership]]). While draining, a release neither re-arms the watchdog nor completes the drain: the watchdog stays paused and the run deadline (or a cancel) is the only bound, so a quiet but valid background child is never aborted as a `drain-timeout` by the inactivity timer. A root `question` call blocks inside the root runner, and a foreground child keeps the root blocked on its `task` tool, so root idle with a question pending can only mean an owned background child, which the ledger already holds. A question still pending when the run completes is rejected by run teardown.

**Teardown.** Each registry disposes only its own family (`disposeRun` / `disposeAll`); the run's approval coordinator and question coordinator each tear down their own entries, and gateway shutdown uses the gate's explicit `disposeAllAcrossFamilies`. A question or approval whose reply POST is still in flight when it is torn down leaves the gate at once; if that reply then fails, the request is rejected once (a question `reject`, a permission `reject` reply — otherwise it would stay pending in OpenCode with no owner), and if it succeeds nothing more is sent. Recovery has one owner: when the deadline had already expired during the claim, the gate's own deadline fail-close (flagged `recoveryStarted` on the entry) already sends the family's deadline reply, so the family sends no second reply; a teardown that lands mid-fail-close also leaves the render and the single terminal event to `retire`. Callers reach the gate only through whole lifecycle operations (`put`, `admit` → `submit`, `settleEcho`, `settleNow`, `retire`); no caller can clear a timer, remove an entry, or emit the terminal notification on its own.

**Cross-surface answering.** Questions are bound to the run that asked them. A web operator whose repo-access check passes for the run's repository can answer or skip any run's question, including a Discord-launched run's; the web route applies that predicate and the gate then accepts a web actor for any scope. A Discord actor can settle only a question from its own thread. A request whose reply is in flight (`claimed`) is absent from the open lists but not settled: a second answer for it gets `already_claimed` (Discord: fixed "Already being answered." copy), never `already_settled`, because the question reopens if that reply fails. The check is scoped to the route's run, so another run's claimed request still reads as an unknown id. Tool approvals keep their channel binding; only questions gain cross-surface answering. A request settles as a whole: one decision carries answers for every question in it.

**Discord shapes and the web fallback.** The native Discord prompt covers a request with a single question: up to 20 options and not `multiple` render as buttons (5 per row), 21–25 options or `multiple` with up to 25 render as one string select, and a control row carries Skip plus "Answer with text…" when a custom answer is allowed (a modal with one 4,000-character input). Everything else — more than one question, more than 25 options, an option with no usable label, or a custom id over Discord's 100-character limit — gets a fixed-copy notice in the thread saying a question is waiting and can be answered on the operator web surface. The notice never carries question text, links the configured public operator origin when one exists, and posts no partial prompt. The entry stays answerable from the web and skips at its deadline as usual. Custom ids are `fb-q:<code>:<requestID>[:<optionIndex>]`; they carry no labels.

**Delivery failure does not settle.** If the Discord post fails terminally (`UnknownChannel` or `MissingAccess`, matched on `DiscordAPIError.code`), the question is not rejected the way an undeliverable approval is: web operators can still answer it and the deadline still skips it. The failure is logged once with ids and the Discord code. Retryable failures are logged and left alone.

**Untrusted text.** Every question and answer string is untrusted plain text. The gateway carries it verbatim apart from length bounding and control-character stripping at the operator-facing build site (`approvals/question-detail.ts`), and never pre-renders it as HTML or Markdown; consumers render it inertly. Discord renders it in embeds, bounded and escaped with `escapeMarkdown`, with `allowedMentions: {parse: []}` on every send and edit. Logs, audit events, errors, and push payloads carry request ids and reason codes only — never question or answer text, and never an effect's raw error string, because an SDK error body can echo the text.

**Caps and index-based answers.** A free-text answer is capped at 4,000 characters and question routes accept a 64 KiB request body; both are enforced before any call to OpenCode, and a refused answer leaves the request pending. An operator names options by zero-based index into the question's `options`, never by label: the labels operators see are bounded and control-stripped and can differ from the raw labels the agent sent, so the gateway maps each index back to the raw label held in the registry before replying. Discord select values are indices for the same reason.

**Restart limitation.** Pending questions are in memory only, like approvals. A gateway restart loses the pending entry and its deadline timer with the run, and startup stale-run recovery handles the run itself. A workspace restart loses OpenCode's pending question; the gateway's deadline still fires and its skip fails closed, and the terminal notification still releases the gauge.

### Checkout Provenance (Gateway + Workspace)

Every run on a repository shares one checkout on a persistent volume (`/workspace/repos/{owner}/{repo}`), so a gateway run must record what it started from. Preparation runs only while holding the repo lock, before `EXECUTING`: `runMention`/`launchWork` (`packages/gateway/src/execute/run.ts`) call `update()` (`packages/gateway/src/workspace-api/client.ts`, `POST /update`) first — never `ensureClone` (`POST /clone`) unconditionally. `ensureClone` runs only when `/update` reports `no-checkout` (e.g. after container recreation), and `/update` is retried against the freshly cloned tree; a fresh clone reporting `no-checkout` again is treated as a workspace bug, not a transient blip. The concurrency gate is keyed by channel, not repo, so preparing before the lock would let another channel or the operator surface touch the tree concurrently (Action runs never touch this checkout). A transport failure throws a `RunCoreError` through the same post-lock failure path as any execution failure; a client-side `/update` timeout reports checkout state as unknown rather than guessing, a rejected control-API bearer (401) maps to `workspace-unavailable`, and everything else invites a retry.

`/update` (`apps/workspace-agent/src/update.ts`) advances an eligible checkout to the remote default branch tip through network-free admission (config inventory, layout, temp-index cleanliness, path-obstruction preflight — `apps/workspace-agent/src/checkout-profile.ts`), a fetch into a root-owned bare mirror, a `pack-objects --stdout | index-pack --stdin --strict` pack-stream import, and a journaled `merge --ff-only --no-overwrite-ignore` fast-forward, returning a discriminated union: `ready` (unchanged or fast-forwarded, with checked remote evidence), `refused` (a reason, no mutation — dirty, detached, non-default-branch, diverged, ahead, unsupported layout/config, obstructed, an initialized submodule, an operation in progress, `needs-recovery`, `maintenance-hold`, or `checkout-substituted`), or `failed` (a reason, plus whether mutation had started). `checkout-substituted` fails the run with its own failure kind before any agent session starts, exactly as `classifyInspectResult` used to. Every other `refused`/`failed` outcome ends the run before `EXECUTING`: `toCheckoutPreparation` (`packages/gateway/src/execute/provenance.ts`) projects it into a `CheckoutPreparation` record persisted with the run's `FAILED` transition, and `formatPreparationRefusedReply`/`formatPreparationFailedReply` (`packages/gateway/src/execute/preparation-reply.ts`) format the reply — every refusal except `maintenance-hold` (and an apply-failed reply whose mutation may have started) names `/fro-bot recover-checkout` and, on Discord, carries a one-click Recover button (`packages/gateway/src/discord/recover-checkout-button.ts`) that reruns the identical flow after a fresh `ManageChannels` check.

A `ready` outcome's own admission gates already guarantee a clean, attached, no-operation-in-progress checkout — exactly the conditions that would otherwise have refused — so the gateway synthesizes `CheckoutProvenance` directly from the `UpdateReady` result rather than an extra round trip; its `remote` is `checked` (branch, SHA, time observed), never `not-checked`. `CheckoutProvenance` keeps meaning "the starting state of a run that reached EXECUTING"; refused/failed attempts land in the separate `checkoutPreparation` field instead (a run cancelled before `EXECUTING` records neither — it never started). The provenance flows three ways: persisted atomically with the `EXECUTING` transition via `detailsPatch`, appended to the prompt (`formatProvenanceForPrompt`), and appended to every final reply as a deterministic code-written "started from" line (`formatProvenanceLine`) — never model-written. Branch names come from an agent-writable checkout: replace backticks in the reply's code span, quote them as a JSON string in the prompt, and cap their length in both. The operator surface exposes both as the optional `OperatorRunStatus.checkoutProvenance`/`checkoutPreparation` fields (contract `1.8.0`) through `parseOperatorCheckoutProvenance`/`parseOperatorCheckoutPreparation` (`packages/gateway/src/operator-contract/provenance.ts`), wire-decoupled DTOs validated field-by-field — malformed or absent data projects to `undefined`, never a cast.

`/inspect` (`inspectCheckout`, `apps/workspace-agent/src/inspect.ts`) remains a standalone read-only diagnostic endpoint, independent of preparation. It runs under the next run's lock before that run's agent starts, against a tree the previous run's agent could write, so treat it as hostile-input code: it runs git as the unprivileged agent uid (not the root service) through the shared invocation in `apps/workspace-agent/src/git-safety.ts` (system/global config off, exactly the one canonical path marked `safe.directory`); it never clones, fetches, checks out, or passes credentials; runs `git status --no-optional-locks --ignore-submodules=all`; neutralizes `core.fsmonitor`, `core.hooksPath`, `core.pager`, and `credential.helper`; and enumerates every configured `filter.<name>` driver (system/global/local/worktree, following includes) fresh before each status call, disabling `clean`/`smudge`/`process` and forcing `required=false` via git's config environment variables rather than `-c` (which splits on the first `=`). Enumeration fails closed — if it cannot list drivers, `status` never runs and the call reports `inspection-failed`. Every git subprocess is bounded and confirmed reaped before a timeout resolves. The accepted cost: in a repo with a real filter (e.g. git-lfs) a stat-changed filtered file reports modified even when its content is not. The checkout types are duplicated between `apps/workspace-agent/src/types.ts` and `packages/gateway/src/workspace-api/types.ts` (the gateway image builds in isolation and cannot import the workspace-agent); `scripts/checkout-types-drift-guard.test.ts` asserts mutual assignability of the real types so drift on either side fails `check-types`.

### Operator Ingress Trust Policy (Gateway)

`packages/gateway/src/web/ingress/` owns the inbound complement of the egress topology (Mitmproxy Egress Topology in [ARCHITECTURE.md](../../ARCHITECTURE.md)): deciding which address on a request is the client. TLS terminates at an infra reverse proxy, so the TCP socket address the operator listener sees is always the proxy's — reading it directly as the identity key collapses every client onto one rate-limit bucket and one OAuth outstanding-attempt slot, which locks the operator out of a live deployment. Reading `X-Forwarded-For` unconditionally is the opposite failure: a spoofable header becomes the identity. The resolution is a single explicit policy value, `OperatorIngressPolicy` (`packages/gateway/src/web/ingress/policy.ts`), carried on `GatewayConfig.operatorWeb.ingressPolicy` and threaded to the health, OAuth, and logout routes. Authenticated routes key on the session identity instead.

The policy is a two-variant union: `direct` (no proxy trusted — the socket is always the client) or `trusted-proxy` with a **non-empty tuple** of peers, `readonly [TrustedProxyAddress, ...TrustedProxyAddress[]]`. A trusted-proxy policy with zero peers is unrepresentable rather than runtime-checked. `loadGatewayConfig()` (`packages/gateway/src/config.ts`) always builds the `trusted-proxy` variant, from `GATEWAY_OPERATOR_TRUSTED_PROXIES` — a comma-separated list of **exact** IPv4/IPv6 addresses, deliberately not CIDR ranges, DNS names, private-network aliases, or a trusted-hop count, so the trust boundary stays bounded and a deployment with dynamic proxy addressing must stabilize its addresses rather than have the gateway trust a whole subnet. The variable is required whenever `operatorWeb` is present and fails loud at startup: missing, empty, unparseable, or an address that cannot identify a real peer (`0.0.0.0`, `::`, `224.0.0.0/4`, `ff00::/8` — `classifyTrustedProxyAddressRejection`) all throw before the config object is constructed; duplicates are deduped rather than rejected. That literal check is explicitly not a reachability proof: it cannot establish that the address is a proxy, that it sits on the request path, or that it sanitizes headers before forwarding. `deploy/validate-stack.sh` check `7i` mirrors only the presence requirement and deliberately does not duplicate the syntax validation, so the two cannot drift.

`resolveClient` (`packages/gateway/src/web/ingress/resolve-client.ts`) is the only production source of a `ResolvedClientAddress` — a branded type whose brand symbol is module-private and marks `resolveClient` as the single intended producer — enforced by code review, not by the compiler, since a type assertion compiles anywhere (`unsafeResolvedClientAddressForTest` is the loudly-named test-only escape hatch). It normalizes the socket address first (missing or unparseable is an `IngressRejection`, never a fallback key), and if the socket is **not** a trusted peer it selects the socket and ignores `X-Forwarded-For` entirely. Only for a trusted peer does it consult the forwarded chain: bounded at 4 KiB and 32 comma-separated entries (a 33rd entry rejects the request — it never truncates), with every entry parsed strictly, so one malformed or non-address token rejects the whole chain rather than being skipped and letting a poisoned entry steer the walk. It then walks `XFF-leftmost … XFF-rightmost, socket` from the socket end leftward and selects the first untrusted address, starting at the rightmost XFF entry because the socket is already known-trusted; traversal stops at the selection, so a forged leftmost claim is never consulted. An all-trusted chain rejects. The rightmost XFF entry is the proxy's record of who connected to it, not the proxy itself — with one reverse-proxy hop it is normally the real client, and a "rightmost is the proxy" reading of this code is wrong.

`packages/gateway/src/web/ingress/canonical-address.ts` is the one parser all three lanes (socket, forwarded entry, configured peer) share, so config-time and request-time identities cannot drift. It establishes canonical _identity_ for equality — normalizing IPv4-mapped IPv6 forms to the IPv4 variant so two spellings of the same client compare equal — and is deliberately distinct from `packages/gateway/src/web/operator-push/ip-classification.ts`, which answers the different question of destination reachability for outbound SSRF defense. It rejects shortened/hex/leading-zero IPv4, ports on either family, bracketed IPv4, zone identifiers including percent-encoded spellings, embedded whitespace or control characters, hostnames, CIDR, and the deprecated IPv4-compatible dotted IPv6 form. Comparison is numeric (`canonicalAddressEquals`), never on raw strings.

`packages/gateway/src/web/ingress/hono-context.ts` is the ingress module's only point of contact with a Hono `Context`: `extractRawIngressInput` pulls socket address and `X-Forwarded-For` (a throwing `getConnInfo` becomes `socketAddress: undefined`, resolved as `socket-unavailable`, never a fallback), and `respondForIngressRejection` maps a rejection to a coarse response — 400 for forwarded-chain failures from a trusted peer, 503 when the socket address is unavailable or unparseable — before any rate-limit bucket or OAuth state is allocated. Both are generic over Hono's Env/Path/Input parameters because `app.use(path, handler)` types Input as `any`, which a concrete `Context` parameter would turn into an implicit-`any` argument at every call site.

Forwarded-host/proto trust on the operator app (`buildOperatorApp`, `packages/gateway/src/web/server.ts`) is decided by peer provenance, not by whether the values happen to match the public origin — matching the public hostname is not proof a request came from the proxy. An untrusted peer supplying any `X-Forwarded-Host`/`-Proto` is rejected 400 outright (headerless direct requests pass through); a trusted peer must supply a complete pair matching `publicOrigin` exactly with `https`. The one exception is narrow and health-only: a fully headerless `/operator/health` request (no XFF, no XFH, no XFP) from a trusted peer is the proxy's own liveness check, and the middleware stashes that verdict under a context key private to `buildOperatorApp` for the route to read verbatim — the route must never re-derive the predicate from its own header reads, or a genuinely incomplete forwarded-client request (valid host/proto but no XFF) could slip into the exception. The health route also runs on its own independent limiter (`OperatorServerDeps.healthRateLimiter`) rather than the shared OAuth/logout `rateLimiter`, so proxy health polling cannot starve sign-in.

Because `/start` and `/callback` resolve through the same resolver and the same policy, a client whose two legs traverse different trusted proxies still binds to one key. A genuine mismatch still happens — mobile handover, VPN toggle, dual-stack switch, CGNAT rotation across a GitHub round trip that can span minutes of 2FA — and dead-ending on 400 would keep the outstanding-attempt slot consumed against the cap until natural expiry, reproducing at small scale the lockout this module exists to prevent. So a mismatch on an otherwise-valid, unconsumed, unexpired state releases the attempt via the same `stateStore.consume()` the success path uses and bounces the browser back to `/start` with `retry=1`, which `/start` stamps onto the _new_ state entry as `bounced`; a second consecutive mismatch terminates with the ordinary coarse 400 instead of bouncing again, so an unstable address cannot loop forever. Every other rejection reason — unknown, already-consumed, or expired state, provider error — is untouched and still 400s, and the `retry=1` marker carries no security weight (a caller setting it unprompted can only make their own next mismatch terminate early). The two outcomes are separate queryable audit reasons, `source_key_mismatch` and `source_key_mismatch_terminal` (`packages/gateway/src/web/audit.ts`), because an address that keeps shifting on one flow is the operationally interesting signal and must not hide behind a count of two same-reason lines. Accepted tradeoff, documented at the code: releasing the attempt means anyone who learns a victim's `state` value can replay the callback from another address and permanently burn that flow — recovery is signing in again, and not releasing it reinstates the cap outage.

**Abuse accounting, shared quotas, and eviction (#1652).** Exact identity and abuse accounting are different questions. A routed IPv6 /64 hands one host 2^64 distinct exact addresses — unbounded free keys for the rate-limit map and the OAuth state store — so counting uses `ResolvedClientAddress.accountingKey` instead (`ipv6/64:<first four groups>`, `ipv4/32:<dotted quad>`; the family prefix keeps derived keys from colliding with an exact canonical string used as a key elsewhere). Consequences to keep in mind: legitimate distinct clients behind one /64 or one IPv4 share a bucket and an outstanding-attempt slot, and the shared OAuth/logout bucket (20/min) is spent by anonymous `/start` and `/callback` traffic as well as authenticated logout. The OAuth binding is not relaxed: `OAuthStateEntry` carries the exact `boundAddress` (compared on callback) and the derived `accountingKey` (counted for the per-key cap of 5) as separate fields, so a client moving within one /64 shares its attempt budget but still trips the exact mismatch bounce.

Both bounded stores admit rather than refuse. The OAuth state store (1,000 entries, 600,000 ms TTL) owns bounded insertion: `/start` reclaims consumed and expired states, enforces the per-key cap, validates the request, and only then — at insertion — evicts the oldest remaining state if the store is full and inserts synchronously. A rejected or invalid start never evicts. An evicted state is simply unknown: its callback gets the ordinary 400 with no bounce, and consume-before-external-await, replay rejection, and the single bounce/retry are unchanged. The rate limiter (`packages/gateway/src/http/rate-limit.ts`, 10,000 keys) has no sweep: expiry is lazy per key, a renewed key is deleted and re-set so it moves to the tail, and a new key at capacity evicts the oldest key (window-renewal FIFO, not LRU — ordinary hits do not promote a key). Both are best-effort under cardinality pressure, and this gives **admission, not guaranteed completion**: a flood can evict an operator's in-flight sign-in attempt (they must start again), and evicting an active rate-limit counter resets that key's bucket. This is consistent with the accepted burned-flow tradeoff above.

### Operator Ingress Invariant: Exact Identity vs. Accounting Key

The unabridged form of invariant 9 in [ARCHITECTURE.md](../../ARCHITECTURE.md).

**No unauthenticated operator-surface client key is ever guessed, and derived accounting keys never stand in for exact identity (gateway ingress).** The client behind every public operator-surface request is a `ResolvedClientAddress` returned by `resolveClient()` (`packages/gateway/src/web/ingress/resolve-client.ts`) against the configured `OperatorIngressPolicy`. That one value carries two deliberately separate things. The **exact canonical identity** (`.canonical`) is the only thing trust and binding decisions use: configured-peer equality (`web/ingress/trusted-proxy-address.ts`) and the OAuth `boundAddress` binding compared on callback. The **derived accounting key** (`.accountingKey`, a branded `AccountingKey`: IPv6 → /64, IPv4 → /32, IPv4-mapped IPv6 already normalized to IPv4) is used only to count or bucket traffic — the health, OAuth start/callback, and logout rate-limit buckets and the OAuth outstanding-attempt slot. Aggregation happens after `resolveClient` has selected the client, never in `canonical-address.ts`, because widening identity there would widen proxy trust (an address in the same /64 as a trusted proxy is not trusted). The one exception is a fully headerless `/operator/health` probe from a trusted peer, which stays keyed on that peer's exact canonical socket address under the health-only limiter: it is a configured proxy, so its key space is bounded by operator configuration, and the unprefixed exact string cannot collide with a prefixed accounting key (see Operator Ingress Trust Policy above). Logout is **not** an unauthenticated route: the session, allowlist, origin, and CSRF guard run first, and only an authenticated logout resolves the client and spends the shared OAuth/logout budget — though anonymous OAuth traffic can still exhaust that shared bucket. An unresolvable request rejects before any bucket or state entry is allocated — it is never collapsed onto a shared fallback key. `GATEWAY_OPERATOR_TRUSTED_PROXIES` is required whenever the operator surface is enabled; `loadGatewayConfig()` throws at startup without it.

## Relationship to Other Surfaces

This surface is one of three ways runs reach the gateway's execution engine, alongside Discord mentions and the GitHub Action. All three converge on the same `launchWork` admission gate and the same approval registry (`registry.handleDecision`) as the single settlement authority — which is exactly why the web tool-approval flow could be added without a parallel approval path: the browser is just another front-end onto the one registry the Discord buttons already drive. The conventions enforced here (functions only, dependency injection, fail-closed defaults, no secret leakage) match the rest of the project; see [[Conventions and Patterns]]. For the per-repo coordination locks (the gateway's `repo.json` and the Action's separate `action.json`), see [[Execution Lifecycle]].
